まず、プロジェクトに小さな機能を追加しました。しかし、大きな変更には、より堅牢なプロセスが必要です。GitHub Copilot app は、組織の既存のフローに沿って作業できるように設計されており、適切なものを適切な方法で構築するのに役立ちます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを実践します。issue から新機能を作り、コードの妥当性と機能の動作を確認し、最終的にプロジェクトへマージします。

> [!NOTE]
> 機能のワークフローでは、引き続き同じセッションを使用します。通常は、作業するファイルの種類ごとに別のセッションや PR を使いますが、ここでは中心的な概念に集中できるよう手順を簡略化します。

このレッスンでは、次のことを行います。

- GitHub issue から新しいエージェントセッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動で検証します。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の `quality-checks` スキルをカスタマイズし、MCP による検証を追加し、QA エージェントを作成して、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが充実し、訪問者がカテゴリーとパブリッシャーでゲームを絞り込める機能が必要になりました。バックログの issue には機能が記載されていますが、カテゴリーを組み合わせる方法など、コーディング前に合意が必要な詳細もあります。Plan モードで決定事項を整理し、Autopilot に範囲を限定した実装を任せます。

## 背景

AI コーディングエージェントを開発フローに導入しても、基本は変わりません。むしろ、基本はさらに重要になります。多くの開発者は、次のようなフローに従います。

1. 必要な作業の詳細が記載された issue を開きます。
2. 構築する内容の計画を作成します。
3. コードを構築してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. プルリクエスト（PR）を作成します。
7. コードのレビューと継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れを変形したものです。

この標準的なアプローチに従うと、AI が生成したコードが要件を満たし、人が作成したコードと同じ審査プロセスを通るようにできます。

## セッションモード

**セッションモード**は、エージェントの自律性を制御します。プロンプトフィールドの下にあるドロップダウンから設定でき、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、続行前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが自律して作業し、入力を待たずにコードの作成、テストの実行、反復を行います。

Plan モードで開始し、計画をレビューしてから、Autopilot で実装します。

## issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これはテンプレートに用意された既存の issue で、新しく作成する必要はありません。
2. **New session** を選択し、更新済みの `main` を基にした **new working tree** を選びます。

    ![GitHub Copilot app の issue ビューで、New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。普段のターミナルでは動作するのにセッションで動作しない場合は、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで、npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てると、Copilot がコードを書く前にアプローチをレビューできます。issue から開始したため、Copilot は機能のリクエストをすでにコンテキストとして持っています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、計画を issue の受け入れ条件と照らし合わせます。カテゴリーとパブリッシャーによる絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認します。複数カテゴリーをどう組み合わせるか、一致するゲームがない場合にどうなるかなど、不明確な動作について話し合います。

計画には、プロジェクトの既存ツールを使った lint、単体テスト、E2E テスト、型チェックを含めます。フィルター機能の実装とテストに範囲を絞り、品質に関する作業を終えてから PR を作成します。計画を承認する前に必要な変更を依頼し、後の検証に備えて issue の URL と合意した補足事項を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンで表示される同等のオプションを選択します。承認によってモードが切り替わるとは限らないため、現在のモードを確認してください。モード表示が **Autopilot** になっていることを確認します。

Copilot が実装を開始します。計画に沿ってコードを生成し、テストを実行しながら作業を進めます。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポート競合が報告された場合は、チェックを完了と判断する前にセットアップの問題を解決します。停止するのは、自分で起動したサーバーだけにしてください。

## 実装をレビューして検証する

生成されたコードも、ほかのコードと同じようにマージ前のレビューが必要です。コードをレビューし、サイトを実行して問題がないことを確認しましょう。

1. **Changes** を開き、フィルター機能の実装とテストを調べます。
2. 複数カテゴリーとパブリッシャーの組み合わせも含め、結果を issue と承認した補足事項に照らし合わせます。変更が既存のリポジトリの指示に従っていることも確認します。
3. lint、単体テスト、E2E テスト、型チェックの出力を確認します。スキップされたチェックは成功ではありません。
4. 実装を受け入れる前に失敗を解決し、該当するチェックを再実行します。Playwright の E2E 設定ではプレビューをビルドして配信し、ローカルサーバーを再利用する場合があります。テスト対象が以前のレッスンではなく、この worktree のサーバーであることを確認してください。

## 新機能を確認する

コードに問題がないように見えても、実際に動作するでしょうか。前と同じようにアプリを起動し、ブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザーキャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリーを選択し、結果が一致することを確認します。フィルターを解除し、パブリッシャーを選択して結果を確認します。
4. カテゴリーとパブリッシャーのフィルターを組み合わせ、結果を issue と承認済みの計画に照らし合わせます。複数カテゴリーが使える場合は、合意した組み合わせの動作も確認します。
5. 結果が一致しない組み合わせを試して、空の状態を確認します。フィルターを解除またはリセットし、すべてのゲームが再表示されることを確認します。
6. 確認が終わったら、次のプロンプトを使い、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンのためにこのセッションを保持する

フィルタリングの PR は、まだ作成またはマージしないでください。レッスン 4 から 8 でも、このセッション、worktree、ブランチを使います。次は、フィルター機能のコードにカスタム指示を適用し、スキルと QA の改善を追加してから、レッスン 8 でまとめた PR を作成してマージします。開発サーバーを停止した後はセッションをそのままにしておき、次のレッスンで同じセッションに戻ってください。

- **Plan** モードで要件を定義しました。
- **Autopilot** モードを使って新機能を実装しました。
- コードをレビューしました。
- ブラウザーキャンバスで機能を手動で検証しました。
